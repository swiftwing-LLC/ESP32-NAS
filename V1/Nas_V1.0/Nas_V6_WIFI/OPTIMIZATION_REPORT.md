# Swiftwing NAS 优化记录

基线：用户提供的 `D:\Esp32 Nas\Nas_V6_WIFI.zip`。Monitor 节点按用户要求由 ESP8266 替换为标准 ESP32 Dev Module / ESP32-WROOM-32；监控状态字段改为 `ESP32`，Master 仍兼容旧 `ESP8266` 状态字段。Wi-Fi 配网协议、通信端口、API 路由、域名及其他页面功能保留。

## 修改

- **Master：**三个 HTML 页面改为在固件中存储 gzip 数据，并为对应响应发送 `Content-Encoding: gzip`。页面解压后与基线逐字节相同。空闲主循环的等待从 1 ms 调为 5 ms；Master 仍持续提供恢复 AP。监控 UI 标签按经过白名单检查的 ESP32/ESP8266 状态字段显示。
- **Node1 / Node2：**上传先汇集到 8 KiB 缓冲区再写入 SD；上传和下载共用原有大小的传输缓冲区。处理短写入、结束时剩余数据、异常中断和未收到结束回调的请求。传输时关闭 Wi-Fi 省电以保持吞吐，结束 2 秒后恢复最低级别的 modem sleep。持续传输数据时每 500 ms 最多检查一次 UDP 节点发现，减少 Master 状态页把忙碌节点标为离线的情况。发现回复只读取一次总容量和已用容量。
- **C3 DNS：**启用 Wi-Fi modem sleep；本地域名 DNS 回复复用接收缓冲区，减少单次调用的栈占用，并为 A 记录增加长度边界检查。等待上游 DNS 时的轮询间隔从 1 ms 调为 5 ms，减少忙转；最坏增加约 4 ms 的响应检测延迟。
- **ESP32 Monitor：**监控程序迁移到标准 ESP32 Dev Module，使用 ESP32 Wi-Fi、HTTPClient 和 EEPROM 库；使用 `WiFi.persistent(false)` 保持显式 EEPROM 配网记录、不把连接配置写入 SDK 区。连接后启用 minimum modem sleep，将空闲循环等待从 1 ms 调为 10 ms。可选 SSD1306 OLED 默认关闭；启用时 SDA/SCL 使用 GPIO21/22。

## 已完成的检查

- Arduino CLI 1.5.1 编译通过：Master、Node1、Node2、ESP32 Monitor 使用 `esp32:esp32:esp32` 和 ESP32 core 3.3.11；C3 使用 `esp32:esp32:esp32c3` 和相同 core。OLED 默认关闭，未启用额外显示库。
- Master 三个 HTML 页面原始总计 50,278 B，gzip 后 15,862 B（减少 68.45%）。逐页解压内容的 SHA-256 与原附件一致。四个页面发送路径均带 gzip 响应头。
- 用本机浏览器通过 gzip 响应检查了文件页、系统状态页和 Wi-Fi 配网页。通过本地模拟 API，文件列表、五板状态、Wi-Fi 扫描列表和选中网络后的密码表单均正常显示；390 px 窄屏下控件可访问，浏览器没有脚本错误。此项验证使用模拟数据，不代表实机 API 已验证。
- Master 及两个存储节点的 `server.on` 路由列表与原附件相同；两个存储节点的共用实现保持一致。
- 用 Arduino CLI 1.5.1 和 ESP32 core 3.3.11 构建：Master 1,019,148 → 985,284 B（减少 33,864 B）；Node1 1,045,716 → 1,046,608 B（增加 892 B）；Node2 1,024,592 → 1,025,464 B（增加 872 B）；C3 1,018,981 → 1,018,967 B（减少 14 B）。这四个原有板型合计减少 32,114 B。新 ESP32 Monitor 构建为 953,760 B，编译期全局 RAM 为 49,088 B；它替换了原 ESP8266 板，因此两种芯片的固件尺寸不直接比较。Master 编译期全局 RAM 增加 16 B，Node1/Node2 各增加 16 B，C3 不变。

## 设备验证

本次没有连接或刷写实物板，也没有可用 SD 卡，因此不能保证实际上传速度、温度、ESP32 Monitor OLED 接线或特定路由器下的广播可靠性。一次局域网只读首页请求返回了 Storage Node 2 状态页，显示 `Storage: NOT READY`；该页没有固件版本标识，无法确认运行的是本次优化版，也不能据此诊断 SD 未就绪的原因。管理 API 需要密钥，本次没有发送密钥或执行写操作。刷写后建议在同一 Wi-Fi/SD 卡条件下：检查登录与页面、恢复 AP 和五板配网、ESP32 Monitor 状态与 OLED、域名解析与节点状态；上传大文件后下载并比对哈希；记录上传 MB/s、空闲与传输时温度，并持续观察节点发现状态。若目标路由器的省电行为影响节点发现，应先对相应板子关闭 Wi-Fi 省电再复测。

原版覆盖同名文件时会先删除旧文件，再写新文件。本次沿用该行为；若覆盖上传时断电、断线或 SD 写入失败，旧文件不会自动恢复。重要文件宜先备份，再做覆盖上传。

若上传客户端暂停发送数据很久，同步 WebServer 可能一直等待下一块数据，期间无法处理节点发现；Master 可能暂时显示该节点离线。传输继续或结束后会恢复发现回复。
