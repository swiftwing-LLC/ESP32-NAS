## V1.3.0：注册需管理员批准（Master UI V1.2.7）

- 从已验证的 V1.2.9 / Master UI V1.2.6 基线开始，仅修改 Master 的账号处理和登录/用户管理页面；四块子板固件保持不变。
- 注册只创建 `pending` 请求，不建立会话。正确输入待批准账号的密码时只返回等待批准提示；批准后才允许登录。拒绝会删除请求，释放用户名和账号槽位；撤销会清除该用户名现存的会话并删除账号。
- 管理员账号 API 分开返回最多 8 条待审核请求和已批准账号，只返回用户名。密码仍使用每账号随机盐和 PBKDF2 派生哈希，不回传密码或哈希。保留 16 个账号总上限。
- 移除启动时自动激活旧 `pending` 账号的迁移逻辑，防止旧请求绕过此次批准要求；已有 `active` 账号不受影响。
- 这是注册权限控制，不是邮件/短信身份验证或 Apple 登录。设备没有可信邮件/短信发送服务；Apple 登录须对 Apple 发回的授权码/身份令牌进行服务器端验证。没有为这些外部服务加入未配置的密钥或假验证。
- 验证通过：Arduino CLI 1.5.1、ESP32 core 3.3.12、标准 ESP32 Dev Module 下 Master 编译成功；使用 1,024,468 B Flash（78%）、48,872 B 全局 RAM（14%），相对 V1.2.9 的 1,015,100 B 增加 9,368 B Flash。

- 账号状态契约检查通过：注册创建 pending 且不发会话；pending 登录被拒绝；仅 admin 可读取待审核/active 列表并执行 approve/reject/revoke；返回内容不含密码或哈希；旧 pending 不再启动时自动转正。静态浏览器预览确认登录申请文案和包含待审核按钮的管理面板布局；预览数据为本地模拟数据。
- 无实机连接，因此不能现场确认远程登录、NVS 持久性或实际网络中的注册操作。上板后需用测试账号分别验证待批准不能进入、批准后可登录、拒绝后不能登录，并确认旧 active 用户仍可用。

**发热相关改动**：Node1/Node2 连上 Bridge、等待 Master 下发家庭 Wi-Fi 时启用 modem sleep；连接家庭 Wi-Fi 前现有代码会再次唤醒无线电。Node1/Node2/C3 找不到 Bridge 时，先关闭无线电等 5 s 再扫描，代替原来无线电保持开启的 1.5 s 等待。正常连接后的上传、节点发现、DNS、风扇控制和页面协议不变。断线恢复的下次尝试最多比原来晚约 3.5 s。另把 Node `/api/info` 的 `total`/`used` 各查询一次并据此计算 `free`，避免每次上传前能力探测再多做两次 FatFs `f_getfree`；JSON 字段与数值关系不变。

**回归证据与边界**：Node1/Node2 的原 multipart 与 `/upload-raw` 处理代码逐字节保持 V1.2.8 内容，Master 程序及全部 UI 资源也逐字节不变；上一版浏览器八种上传模拟仍针对同一页面源码。本轮四块子板默认构建和 Monitor 可选配置构建通过；静态核对四份引导读取器一致、Master 响应包含长度、最大合法正文可容纳。没有实机，所以不能确认实际 Bootstrap 耗时、上传 MB/s、空闲/掉线电流或温度。无线电关闭只改善 Bridge 不可用时的重试阶段；若五板正常联网仍烫，Master 常开的恢复 AP、板载线性稳压器、SD 模块和供电接点都可能主导发热，固件不能据此宣称已降至正常温度。

**上板复核**：V1.2.8 与 V1.2.9 在同一供电、路由器、SD 卡和室温下分别测五板空闲及掉线电流/温度；实测 Bridge 缺失与恢复时的重试时间、从 Bridge 获取配置及五板重新联网。再用同一大文件测上传 MB/s，下载核对 SHA-256，检查 Master 页面、账号、C3 DNS、节点发现、Monitor 风扇。记录发热点是 ESP 芯片、板载稳压器、SD 模块还是接头；若热点在供电硬件，须按实测电压/电流与器件额定值处理。

## 修改

- **Master：**三个 HTML 页面改为在固件中存储 gzip 数据，并为对应响应发送 `Content-Encoding: gzip`。页面解压后与基线逐字节相同。空闲主循环的等待从 1 ms 调为 5 ms；Master 仍持续提供恢复 AP。监控 UI 标签按经过白名单检查的 ESP32/ESP8266 状态字段显示。
- **Node1 / Node2：**上传先汇集到 8 KiB 缓冲区再写入 SD；上传和下载共用原有大小的传输缓冲区。处理短写入、结束时剩余数据、异常中断和未收到结束回调的请求。传输时关闭 Wi-Fi 省电以保持吞吐，结束 2 秒后恢复最低级别的 modem sleep。持续传输数据时每 500 ms 最多检查一次 UDP 节点发现，减少 Master 状态页把忙碌节点标为离线的情况。发现回复只读取一次总容量和已用容量。
- **C3 DNS：**启用 Wi-Fi modem sleep；本地域名 DNS 回复复用接收缓冲区，减少单次调用的栈占用，并为 A 记录增加长度边界检查。等待上游 DNS 时的轮询间隔从 1 ms 调为 5 ms，减少忙转；最坏增加约 4 ms 的响应检测延迟。
- **ESP32 Monitor：**监控程序迁移到标准 ESP32 Dev Module，使用 ESP32 Wi-Fi、HTTPClient 和 EEPROM 库；使用 `WiFi.persistent(false)` 保持显式 EEPROM 配网记录、不把连接配置写入 SDK 区。连接后启用 minimum modem sleep，将空闲循环等待从 1 ms 调为 10 ms。可选 SSD1306 OLED 默认关闭；启用时 SDA/SCL 使用 GPIO21/22。

## 设备验证

本次没有连接或刷写实物板，也没有可用 SD 卡，因此不能保证实际上传速度、温度、ESP32 Monitor OLED 接线或特定路由器下的广播可靠性。一次局域网只读首页请求返回了 Storage Node 2 状态页，显示 `Storage: NOT READY`；该页没有固件版本标识，无法确认运行的是本次优化版，也不能据此诊断 SD 未就绪的原因。管理 API 需要密钥，本次没有发送密钥或执行写操作。刷写后建议在同一 Wi-Fi/SD 卡条件下：检查登录与页面、恢复 AP 和五板配网、ESP32 Monitor 状态与 OLED、域名解析与节点状态；上传大文件后下载并比对哈希；记录上传 MB/s、空闲与传输时温度，并持续观察节点发现状态。若目标路由器的省电行为影响节点发现，应先对相应板子关闭 Wi-Fi 省电再复测。

原版覆盖同名文件时会先删除旧文件，再写新文件。本次沿用该行为；若覆盖上传时断电、断线或 SD 写入失败，旧文件不会自动恢复。重要文件宜先备份，再做覆盖上传。

若上传客户端暂停发送数据很久，同步 WebServer 可能一直等待下一块数据，期间无法处理节点发现；Master 可能暂时显示该节点离线。传输继续或结束后会恢复发现回复。
